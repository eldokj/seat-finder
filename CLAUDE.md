# Exam Seat Finder

College daily exam-seating lookup system built around a rule-based seating
engine. Students search by register number only (no login); admins
(Supabase Auth) upload one Consolidated Exam + Student Data Excel file (the
only exam-data import workflow — see the Import/Export architecture bullet
below) and use a configurable rule engine (or manual placement) to seat
students into rooms.

- Being built in 12 reviewable phases — see README.md "Development phases".
  The list was revised after Phase 3 when the seating model was redesigned
  (Phase 4) around Examination Period → Daily Examination Event → Master
  Timetable Record, replacing the old one-row-per-course `exams` table.
  Don't jump ahead to a later phase's functionality without it being asked
  for.
- Database schema: `supabase/migrations/0001` through `0006`, documented in
  `docs/SCHEMA.md`. Key shape: a `daily_examination_event` is one (date,
  session) slot that can hold MULTIPLE `master_timetable_records` (one per
  programme+course) — never assume one event = one course. A student's
  room/seat is event-specific, never permanent — always via
  `seat_allocations`, never a column on `students`.
- `seat_allocations` has three logical states on ONE table (no separate
  registration table): participating (room_id/room_seat_id/seat_no all
  null) → room-assigned (room_id set) → seated (room_seat_id/seat_no also
  set). Only "seated" counts as Allocated in any report/stat.
- `rooms` (renamed from `halls` in 0003) is the physical room; `room_seats`
  is its optional detailed grid (a room can be fully usable via
  `usable_seats` alone with zero `room_seats` rows, before a layout exists).
- Branding (college name/logo/COE office name) is never hardcoded — always
  read via `src/lib/config/branding.ts`.
- Three Supabase client flavors in `src/lib/supabase/`: `client.ts` (browser,
  anon key), `server.ts` (server components/routes, respects the signed-in
  user + RLS), `admin.ts` (service-role, bypasses RLS, server-only, use
  sparingly and only in trusted server code).
- User-facing copy for the student search flow is centralized in
  `src/lib/config/messages.ts` — reuse it rather than re-typing strings.
- RLS: every table has admin-scoped policies (any active `admin_profiles`
  row gets full access via `is_active_admin()`, established in `0002`,
  extended to every new table through `0006`). A public search function for
  students lands once the seating allocation engine exists. `admin_profiles`
  itself has no insert/update policy for any role — admin accounts are
  provisioned manually (docs/DEPLOYMENT.md), never self-service. Whenever a
  table is dropped and recreated (e.g. `seat_allocations` in `0005`), RLS
  must be re-enabled immediately in the same migration — a fresh
  `CREATE TABLE` starts with RLS off, which on Supabase means open access
  via default grants, not closed.
- Admin routes: `app/admin/login` is public; everything under
  `app/admin/(dashboard)/` is protected by that route group's `layout.tsx`
  calling `getAdminSession()` (`src/lib/admin/auth.ts`). New protected admin
  pages go inside `(dashboard)/` to inherit the guard automatically — Route
  Handlers do NOT inherit layouts, so any future `app/api/admin/**/route.ts`
  must call `getAdminSession()` itself and return 401 JSON if null.
  `src/proxy.ts` (Next 16 renamed "middleware" → "proxy" — same mechanism)
  only refreshes the session cookie for `/admin/*` — never widen that
  matcher to the public student path (performance).
- Use `logAuditEvent()` (`src/lib/admin/audit.ts`) for every auditable admin
  action (login/logout, room/daily-event CRUD + status transitions already
  wired) — reuse it rather than inserting into `audit_logs` directly.
- `src/types/database.ts`: every Row/Insert/Update shape MUST be `type`, not
  `interface` — postgrest-js's result inference silently returns `never` for
  interfaces (see docs/SCHEMA.md "Gotcha for future edits"). Bit us once
  already; don't reintroduce it. Same file: don't use PostgREST embedded
  selects (`.select("*, other_table(count)")`) — our `Database` type
  declares empty `Relationships` everywhere, so embeds don't type-check
  reliably; use a separate per-row count query instead (see
  `daily-events/page.tsx` for the pattern).
- Dynamic routes use Next 16's typed-route helpers (`PageProps<'/admin/rooms/[id]'>`,
  `await props.params`). These types come from `.next/types/`, generated by
  `next dev`/`next build`/`next typegen` — after adding a NEW dynamic route
  folder, run `npx next typegen` before `tsc --noEmit` or the route literal
  won't be recognized yet (`tsc` alone doesn't trigger generation).
- Status-changing admin actions (publish/unpublish/close/delete/deactivate)
  follow one pattern: a plain (non-useActionState) server action bound with
  `.bind(null, id)`, wrapped in a `<form>` whose submit button is
  `ConfirmButton` (native `confirm()` dialog), redirecting back to the
  detail page with `?error=` on failure. Reuse this rather than inventing a
  new confirmation mechanism — the Seating Allocation / rule engine phases
  should build on it too.
- I (Claude) cannot execute raw SQL/DDL against the live Supabase project —
  the service-role key only reaches PostgREST (table reads/writes), not
  arbitrary SQL. Every migration gets pasted into the Supabase SQL Editor by
  the user, same as 0001–0007. Don't imply otherwise or claim a migration
  "ran" without the user confirming it.
- Excel import (Phase 5): `xlsx` is installed from SheetJS's own CDN
  (`https://cdn.sheetjs.com/...tgz`), NOT the npm registry — the last
  npm-published version (0.18.5) has two unpatched CVEs. Don't
  `npm install xlsx` casually; it'll silently reintroduce them.
- Import pipeline architecture: parsing/validation/classification logic is
  pure functions with zero I/O (`src/lib/validation/consolidated-import.ts`,
  `import-normalize.ts`, `timetable-roster-comparison.ts`) — fully
  unit-testable without a live DB, see their `.test.ts` files. The I/O layer
  (`src/lib/excel/consolidated-pipeline.ts`) wraps them with actual Supabase
  reads. Preview and Confirm both call the exact same pipeline function —
  Confirm just also performs writes — so they can never drift apart. Follow
  this split for any future import type (don't inline validation logic into
  a server action). The old standalone Master Timetable / Student Roster
  importers (`timetable-import.ts`/`timetable-pipeline.ts`,
  `roster-import.ts`/`roster-pipeline.ts`, `app/admin/(dashboard)/timetable/`,
  `.../roster/`) were removed as a product decision — Consolidated Import is
  now the only exam-data import workflow. A few pure types/helpers that
  originally lived in those files (`RowSeverity`, `RowClassification`,
  `TargetExaminationPeriod`, `sessionKey`, `ExistingStudent`) are still
  genuinely shared by `consolidated-import.ts`, `room-import.ts`, and
  `room-layout-import.ts` — they now live in
  `src/lib/validation/import-shared.ts`, not duplicated per-file.
- `seat_allocations` rows created by the Consolidated importer are always
  stage-① "participating" (room_id/room_seat_id/seat_no null) — the
  importer never assigns a seat. Room/seat assignment is the Seating
  Allocation phase.
- Vitest config must be `vitest.config.mts` (not `.ts`) — the plain `.ts`
  extension gets loaded via CJS by Vite's config loader in this project
  (no `"type": "module"` in package.json) and crashes on an ESM-only
  transitive dependency. `.mts` forces ESM loading and avoids it.
- Audit policy (Phase 10): `logAuditEvent()` is called for every *mutating*
  admin action (create/update/delete/status-change, across every phase
  since Phase 2) — that's unconditional, not optional. Report *views* are
  the one deliberate exception where reads get logged too (`report_viewed`
  action, since Phase 9) — because a report can expose a full seating list,
  logging who looked at it is treated as worth the extra row. No other
  read path is audited (room lists, student search, etc.) — logging every
  page view would flood `audit_logs` for no real benefit. If a new
  feature's reads are sensitive enough to warrant auditing, follow the
  Phase 9 report-view precedent explicitly rather than assuming silence
  means "don't bother."
- Rate limiting (Phase 10): `src/lib/rate-limit.ts`'s `InMemoryRateLimiter`
  is deliberately per-process, not distributed — see that file's doc
  comment before reaching for it anywhere new. It's sized for this
  project's current single-college traffic; don't treat it as a hard
  guarantee under serverless multi-instance load.
- Import/Export architecture (inserted between Phase 9 and Phase 10's
  remaining work): a **Consolidated Exam + Student Data** import
  (`src/lib/validation/consolidated-import.ts` + `consolidated-pipeline.ts`,
  `app/admin/(dashboard)/exam-data/`) is the **only** exam-data import
  workflow — the original two-step Master Timetable / Student Roster
  importers were fully removed (a later product decision; they briefly
  coexisted as "legacy" before that). It writes to the exact same tables
  (`master_timetable_records`, `students`, `seat_allocations`) those two
  screens used to — `master_timetable_records` and `students` remain
  ordinary internal tables, this is only a change to the admin's upload
  experience, not the schema. Strength is never a column, always computed
  by grouping rows on (Date, Session, Programme, Course Code).
  `import_batches.import_type` gained a third value, `'consolidated'`, via
  migration `0009` — additive only, nothing else about that table changed;
  `'timetable'`/`'roster'` remain valid historical values for old rows but
  nothing writes them anymore. Also added: Room Master import/export
  (`room-import.ts`/`room-pipeline.ts` — Rows/Columns there are
  informational-only, never touch `rooms.rows`/`rooms.columns` or
  `room_seats`, and are ignored once a room has a saved layout), Room
  Layout import/export (`room-layout-import.ts`/`room-layout-pipeline.ts` —
  the write path reuses the existing `saveRoomLayoutAction` directly, one
  call per room, so occupied-seat protection is never duplicated), and
  Seating Rules JSON export/import (`seating-rules-io.ts`'s
  `saveSeatingRuleSetFromInput`, validated against the same
  `seatingRuleSetInputSchema` the form uses — no new table). Rooms/Layout/
  Rules imports have no `daily_examination_event_id` to hang an
  `import_batches` row off, so their history is one summarizing
  `audit_logs` entry per import instead (`room_master_imported`,
  `room_layout_imported`) — don't stretch `import_batches` nullable to fit
  them.
